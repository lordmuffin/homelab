# Gitea Terraform Workflows

This directory contains Gitea Actions workflows for managing Terraform infrastructure with Azure Storage backend.

## Overview

The workflows provide automated Terraform plan and apply capabilities with the following features:

- **Azure Storage Backend**: Remote state storage in Azure Storage Account
- **Multi-Environment Support**: Separate configurations for `dev-lab` and `prod-lab`
- **Module-Based Architecture**: Support for individual Terraform modules
- **Security**: Azure OIDC authentication and secret management
- **PR Integration**: Plan results commented on pull requests
- **Safety Controls**: Multiple validation steps and approval gates

## Workflows

### 🔍 terraform-plan.yml

**Purpose**: Validates Terraform configurations and generates plans for review

**Triggers**:
- Pull requests targeting `main` or `develop` branches
- Pushes to `feature/*` branches
- Changes to `terraform/**` or workflow files

**Features**:
- Runs `terraform plan` for all environment/module combinations
- Posts plan results as PR comments
- Uploads plan artifacts for later use
- Includes security scanning with tfsec
- Matrix strategy for parallel execution

**Matrix Configuration**:
```yaml
strategy:
  matrix:
    environment: [dev-lab, prod-lab]
    module: [main, vault, unifi, vultr, b2]
```

### 🚀 terraform-apply.yml

**Purpose**: Applies Terraform changes to infrastructure

**Triggers**:
- Pushes to `main` branch (automatic deployment)
- Manual workflow dispatch (controlled deployment)

**Features**:
- Pre-apply security checks and validations
- Downloads plan artifacts from previous runs
- Generates fresh plans before apply
- Deployment summaries and notifications
- Environment-specific deployment URLs
- Post-apply verification steps

**Manual Deployment**:
```bash
# Workflow dispatch inputs
environment: dev-lab | prod-lab
module: main | vault | unifi | vultr | b2
confirm_apply: "apply"  # Required confirmation
```

### 🔧 terraform-setup.yml

**Purpose**: Shared composite action for common Terraform setup steps

**Features**:
- Azure authentication and backend verification
- Terraform installation and configuration
- Path computation for different modules
- Format checking and validation
- State key generation for Azure backend

## Required Secrets

Configure these secrets in your Gitea repository:

### Azure Authentication
```
AZURE_CLIENT_ID          # Azure service principal client ID
AZURE_TENANT_ID          # Azure tenant ID
AZURE_SUBSCRIPTION_ID    # Azure subscription ID
```

### Azure Backend Storage
```
AZURE_BACKEND_RESOURCE_GROUP     # Resource group containing storage account
AZURE_BACKEND_STORAGE_ACCOUNT    # Storage account name for Terraform state
AZURE_BACKEND_CONTAINER_NAME     # Container name for state files
```

### Terraform Variables
```
RACKSPACE_API_KEY        # API key for Rackspace provider
```

### Backend Configuration
The workflows automatically generate backend configuration:

```hcl
terraform {
  backend "azurerm" {
    resource_group_name  = "your-resource-group"
    storage_account_name = "your-storage-account"
    container_name       = "terraform-state"
    key                  = "dev-lab/main.tfstate"
  }
}
```

## Usage Examples

### Typical Workflow

1. **Create Feature Branch**:
   ```bash
   git checkout -b feature/add-new-infrastructure
   ```

2. **Make Terraform Changes**:
   ```bash
   # Edit terraform files
   vim terraform/main.tf
   ```

3. **Push Changes**:
   ```bash
   git add .
   git commit -m "Add new infrastructure"
   git push origin feature/add-new-infrastructure
   ```

4. **Create Pull Request**:
   - Workflows automatically run `terraform plan`
   - Plan results posted as PR comments
   - Review plan output before merging

5. **Merge to Main**:
   - Automatic `terraform apply` runs on merge
   - Infrastructure deployed to all environments

### Manual Deployment

For controlled deployments to specific environments:

1. Navigate to **Actions** → **Terraform Apply**
2. Click **Run workflow**
3. Select:
   - **Environment**: `dev-lab` or `prod-lab`
   - **Module**: `main`, `vault`, `unifi`, `vultr`, or `b2`
   - **Confirmation**: Type `apply`
4. Click **Run workflow**

### Emergency Procedures

#### Plan-Only Run
```bash
# Create a PR to see plans without applying
git checkout -b emergency/review-changes
# Make temporary changes to trigger planning
git push origin emergency/review-changes
# Review plan outputs in PR comments
```

#### Rollback Infrastructure
```bash
# Use manual deployment with previous configuration
# Or restore from version control:
git revert <commit-hash>
git push origin main
```

- **Purpose**: Testing and development
- **Protection**: Standard branch protection
- **Modules**: All except `b2` (production-only)

### Production Lab (prod-lab)
- **Purpose**: Production infrastructure
- **Protection**: Enhanced branch protection with approvals
- **Modules**: All modules including `b2`

## Security Features

### Authentication
- Azure OIDC for secure, keyless authentication
- Service principal with minimal required permissions
- No long-lived secrets for Azure access

### State Security
- State files encrypted at rest in Azure Storage
- Access controlled via Azure RBAC
- State locking to prevent concurrent modifications

### Workflow Security
- Branch protection rules enforced
- Required status checks before merging
- Manual confirmation for manual deployments
- Pre-apply security scanning with tfsec

### Secret Management
- All sensitive values stored as Gitea secrets
- Secrets marked as sensitive in Terraform
- No secrets logged in workflow outputs

## Troubleshooting

### Common Issues

#### Plan Failures
```bash
# Check formatting
terraform fmt -check -recursive

# Validate configuration
terraform validate

# Check Azure permissions
az storage account show --name <storage-account> --resource-group <rg>
```

#### Apply Failures
```bash
# Check state lock
terraform force-unlock <lock-id>

# Verify backend access
az storage container show --name <container> --account-name <account>

# Manual recovery
terraform refresh
terraform plan
```

#### Permission Issues
```bash
# Verify Azure login
az account show

# Check resource access
az role assignment list --assignee <client-id>

# Test storage access
az storage blob list --container-name <container> --account-name <account>
```

### Debugging Workflows

1. **Enable Debug Logging**:
   - Set repository variable: `ACTIONS_RUNNER_DEBUG=true`
   - Set repository variable: `ACTIONS_STEP_DEBUG=true`

2. **Check Workflow Artifacts**:
   - Download plan files from workflow runs
   - Review apply summaries for detailed output

3. **Manual State Inspection**:
   ```bash
   # Download state file from Azure
   az storage blob download \
     --container-name <container> \
     --name dev-lab/main.tfstate \
     --file local-state.tfstate \
     --account-name <account>
   ```

## Best Practices

### Development Workflow
1. Always create feature branches for changes
2. Review plan outputs before merging
3. Test changes in dev-lab first
4. Use descriptive commit messages

### Production Deployments
1. Require multiple approvals for production
2. Use manual deployments for critical changes
3. Monitor deployment progress
4. Have rollback procedures ready

### State Management
1. Never edit state files manually
2. Use workspace isolation for environments
3. Regular state backups to separate location
4. Document state recovery procedures

### Security
1. Rotate Azure credentials regularly
2. Monitor workflow execution logs
3. Use least privilege for service principals
4. Regular security scanning and updates
